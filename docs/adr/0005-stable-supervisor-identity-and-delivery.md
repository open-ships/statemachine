# Stable Supervisor identity and delivery

The first stable baseline is 1.4.0. Tags through 1.3.2 remain unchanged prerelease history. We keep pure Machine.Next and the existing module path, and document migration instead of retaining Machine.Fire or introducing compatibility shims. Subsequent stable releases follow semantic versioning.

A persisted restart counter cannot guarantee unique identities: the same clean Snapshot can be restored twice before either process saves its newer counters. Each construction or restoration therefore has a cryptographically random IncarnationID. Attempt identity is (ExecutionID, IncarnationID, Sequence); Record identity is (ExecutionID, IncarnationID, Seq). Restarts remains useful evidence but is not a uniqueness authority or a fencing token. Snapshot schema 2 carries the identity and original Change start time. Startup and accepted guard refusals also save their high-water marks when Journal delivery succeeds.

An Operation owns its decision and the complete Journal/Recorder publication pipeline. A timeout only bounds the wait: the callback retains its lease until it actually ends. Admission and recovery consult that ownership. Trip and verification expiry reserve publication ownership at the decision instant, so recovery cannot race a later callback start. Expiry detected synchronously by Verify uses the same decision and finalization implementation as timer-driven expiry, preserving the original Change and known Issue completion. Its reporting reservation does not own the return of an enclosing Issue call; callbacks can borrow that Operation for accounting without releasing its public-call ownership.

Journal and Recorder each have one fail-fast delivery gate. No new callback enters a busy sink, including a Recorder reentering Trip; the decision remains in bounded memory and Status exposes the delivery failure. This prevents a late old Journal write from overlapping a later prepare and bounds abandoned adapter goroutines to one per sink per Supervisor. We deliberately do not queue or automatically retry delivery. A failed or skipped closure can leave a clean or in-doubt saved Snapshot, so startup always requires application reconciliation. These gates are process-local and do not replace an external exclusive writer or fencing.

For selected Attempts and their Verify or Adopt outcomes, Result.Change, Record.Change, and Fault.Change preserve the original command revision and start time. PendingSnapshot preserves the original external Attempt identity across restoration, even when its incarnation differs from the restored Supervisor's new incarnation. Records without a selected command may carry a zero or operation-specific Change. Operation timing, resulting revision, and adjudication outcome are separate fields. Adopt and Override commit and increment revision even when their target equals the current state; adoption is explicit reconciliation, not a claim that Verify succeeded. History retains the highest causal Seq values, not the latest arrivals. Sequence exhaustion refuses admission and ultimately stops stamping rather than wrapping an identity.

Application error formatting is also application code. Callback error text is captured within the owned callback budget; later record and fault construction does not invoke arbitrary Error or String methods under the state lock. Raw custom Trip errors retain their original cause and use a type description for stored text.

The Machine, Instance, Runtime, Store, Statechart, and Supervisor remain distinct domain modules. Shared observer containment and statechart hierarchy internals deepen those modules without unifying their different commit semantics.
